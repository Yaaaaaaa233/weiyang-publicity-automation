# 架构与迁移

## 服务职责

第一版将提供两个 Docker 服务；目前已有 `browser` 的配置及命令接口，`workflow` 待实现：

- `workflow`：任务持久化、规则检查、报告、调度与独立 agent 执行程序。
- `browser`：专用浏览器、页面观察和动作执行，并提供经配置的人工查看/登录入口。

宿主机已提供 SQLite 任务账本、报告和 JSON 交接命令，见 `docs/tasks.md`。这些工具尚未组成独立模型执行循环，也没有容器化为 `workflow` 服务。

本机当前 Codex 聊天已配置每天 15:10 的定时接续（原 17:00 已调整），agent 负责实时预约读取及平台操作，`scripts/daily_check.py` 负责收稿完整性判定。`scripts/notify_wecom.py` 的企业微信单向提醒已实际接通，不包含消息输入或交互任务入口。运行与迁移说明见 `docs/daily-run.md` 和 `docs/wecom-notifications.md`；首次无人值守仍待验收。桌面 app 定时入口不随 Git 自动迁移，换执行节点时须先停用旧入口。

BOT 后续作为可选入口加入，消息转换为持久化任务。服务在 Docker 内部网络通信；人工入口按需要仅绑定宿主机本地地址。

模型负责理解与决策；容器中的程序运行脚本和操作浏览器。当前桌面聊天中的 Computer Use 不自动成为容器内工具，需要独立的浏览器工具接口及 agent 接入适配。

## 数据与恢复

业务规则随代码发布。稿件、素材、报告、截图、任务数据库与浏览器状态保存到独立目录或数据卷。密钥在目标设备单独配置。

每个任务记录来源、版本、规则版本、当前步骤、完成证据、待人工事项和平台草稿定位。界面保存结果不确定时，先核对实际结果，再决定重试。

初期只支持一个活跃执行节点，同一任务只由一个执行者处理。

## 换电脑

停止旧节点写入 → 导出一致的任务数据库和文件 → 在新电脑安装 Docker → 启动匹配 CPU 架构的镜像 → 恢复数据并配置凭据 → 核对登录与平台实际状态 → 接续任务。

浏览器状态迁移后可能需要重新登录；不能将其当成永久有效的登录保证。

## 换 agent

业务脚本、规则、任务数据和浏览器能力接口保留。新 agent 读取交接记录，重新观察页面，从已验证的检查点继续。不同 agent 的模型和工具调用方式由适配层处理。

## 验收顺序

基础 Docker 环境 → 浏览器工具 → 单篇稿件检查 → 中断恢复 → 草稿保存验证 → Windows/macOS 迁移 → 定时调度 → BOT 接入。

最终发布保留人工。项目不需要对公网开放自建服务；访问平台和模型仍需联网。
