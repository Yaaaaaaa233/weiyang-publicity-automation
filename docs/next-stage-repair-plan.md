## 1. 正文读取的具体修法

1. 保留浏览器位置选择器格式，依据已经定位到的 vessel 节点完整路径求父级，不再从路径文本猜类名。祖先尝试次数必须实际受限。
2. 从最小范围向上寻找能容纳正文、标题及封面元数据的范围。每次核对稿件 URL/ID、唯一正文节点、元数据和截断标记；不能只检查“存在标题”便认定足够。
3. 明确记录最终作用域、尝试次数、节点数、正文长度及失败类别。对无法形成完整范围的情况给出具体结果，不默默回落整页后再次产生泛化错误。
4. 保留正文与段落截断、图片未加载、账号/稿件不符等保护。扩大上限不作为默认修复手段。较大祖先包含较小祖先，遇超限后的重试策略需有实际依据。
5. 检查异常退出时的浏览器窗口收尾：只关闭本次创建且身份核对通过的窗口，保留原异常和清理结果，避免失败轮次不断积累编辑器窗口。

验证分三层：

- **离线回归**：私有真实快照复现 r9 故障；公开测试仅保留脱敏结构和真实格式的位置路径，包含普通稿、复杂稿、标题/封面分离、正文截断、错误 ID、图片未完成等场景。
- **桥接契约验证**：用本地模拟页面实际执行浏览器读取脚本，再交给 Python 消费，验证 JavaScript 输出与 Python 输入一致，避免双方各自用假数据通过。
- **Windows 只读实测**：用已有复杂合辑和普通稿，完整读取并核对结果，不创建稿件、不转存、不发送业务结果通知。历史快照仅用作回归样本，不能当作本轮实时证据。

## 2. 下游与接续收口

修复正文后，检查既有 agent 检查点是否能被同一执行者连续处理：正文证据 → 身份决策 → `--decisions` 接续；格式问题 → 实际观察 → 限定修复动作 → 再验收。这些是 agent 工作步骤，不能误报为必须人工审批。

优先回放已有事故：保存副本自动附加“ - 拷贝”、隐藏/重复选稿控件、长通知分段、提交结果未知、正文采集失败及观察过期。检查每种情况的状态、通知、锁释放和再次进入行为。

继续保留真实时间和 60 分钟观察有效期；过期重新读取，不改时间。已有副本按账号、业务日期及源稿映射复用；同步预留或提交存在时，恢复只检查结果，不再次提交。只对本阶段可复现的缺陷修改代码，未发现缺陷的规则保留。

账本作为防重依据，必须验收：

- 保存账号、业务日期、run_id、源稿 ID、副本 ID、组合顺序、提交记录、同步结果证据与通知回执，不能仅凭标题判重。
- 区分提交前、已预留提交、已提交、成功及结果未知；写入失败或程序中断后，先核对平台与既有记录，不能因缺少“成功”记录再次提交。
- 在私有测试目录验证换 run、换执行者和迁移后的恢复：加载原账本和检查点，复用原映射，已提交组合不重发。模拟用账本不能覆盖真实运行账本。
- 迁移必须保留任务账本、副本映射、同步去重记录及通知回执；仅克隆 Git 不代表迁移完成。首次空账本与迁移遗漏要明确区分，不能把丢失历史记录自动理解成从未处理。
- 同时只允许一个业务执行者。人工在系统外完成的转存不天然存在于账本，应明确其覆盖边界；需要纳入防重时补记有依据的记录，不靠平台标签猜测。

## 4. 完整验收

只读实测通过后，固定执行版本及完整任务提示词，将这份提示词直接发到 Windows 当前执行会话。该提示词随后原样用于定时业务执行，只替换实际运行参数；记录提示词版本/哈希、投递方式和实际开始时间。无需为了本次业务验收创建或等待临时定时任务。

若已跨日，读取新的当天预约，不伪装成 10 月 12 日业务。使用稳定 run_id，恢复沿用原 run，新检查用新 run；先检查同步去重记录，避免重发已经转存的组合。当前会话发起新的验收前，应检查是否还有旧业务执行或临近的定时触发。

调试阶段以离线回放和真实只读验证为主，不提前提交验收组合。若调试已经产生副本或同步提交，沿用真实账本接续；不能清空记录或重复转存来制造一轮“从头成功”。

提示词需明确完整七环、账本位置、授权操作、身份/格式检查点接续、通知和日志收尾。投递后由同一执行 agent 自动完成语义决策及限定修复动作，不再由人逐步给命令。若运行途中人工审批、追加救场指令或临时改代码，该轮记为调试，不能算无人值守成功；修复后再按账本安全安排验收。

验收覆盖：读表 → 正文匹配 → 独立副本 → 基础排版及保存重开 → 顺序和封面组合 → 一次同步 → 企业微信结果。

- 标注头条则置首；未标头条按预约行序，并给非阻断提醒；多个头条仍阻断。
- 标题不同但正文等证据确认同稿，记录两种标题和依据，仅提醒人工注意。
- 正文、内容图片及顺序保存重开核对通过；复杂结构无法验证时如实停下。
- 同步必须有实际明确成功证据；没有则 `awaiting_confirmation`，不自行确认、不重提交。流程能正确停下，不等于全成功验收通过。
- 公众号后台与最终发布仍由使用者负责，验收不操作后台、不群发。
- 本轮业务结果通知有真实 accepted 回执；如需收稿中间通知，必须与最终结果区分并记录，不能重复发送同一事件。
- 真实账本记录与平台证据一致；只读重复检查、离线恢复回放及迁移回放不会增加同步提交次数。
- 回传包含版本、实际时间、各环证据、审批/人工介入数量、提交次数、通知回执、未完成项及下一步。

“转存好”平台标签按使用者要求保持关闭，不是独立验收项，也不是三天试运行的前置条件。本阶段不启用或操作标签；账本防重、接续及迁移纳入验收。

直接投递提示词验收的是业务执行路径，报告注明“会话直接投递”。它不证明新的定时触发成功；会话存活、休眠/电源、触发及重复投递等调度条件单独检查，并在三天实际定时运行中记录，避免把两种验收混为一谈。
