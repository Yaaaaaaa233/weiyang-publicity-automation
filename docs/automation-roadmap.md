# 全流程脚本化梳理（2026-10-05）

本记录依据当前源码与已完成的验证。2026-10-05 后续已完成建议前三项：`wps_read.py`、`xiumi_scan.py`、`daily_run.py`，Mac Docker 浏览器完整读取链路及通知预览通过。具体用法与边界见 [统一检查入口](daily-runner.md)；下面实施顺序保留设计背景，第四、第五项尚需接续。使用者指定本轮只做封装，不处理或调整既有定时任务。每日业务止于预约检查、收稿和基础整理，公众号转存是独立步骤，最终发布由人工完成。

## 目标流程

触发 → 检查执行节点与浏览器占用 → 读取当日预约 → 校验日期、完整性及排序要求 → 查秀米候选 → 收稿完整性判定 → 整理独立副本 → 保存重开验收 → 发送本轮结果 → 释放任务并交接。

无预约直接记录并通知。来源失败、缺稿、周次不符或版本歧义停止整组整理并通知。收齐只是允许开始整理；保存后核对全部通过才报告整理完成。公众号组合/转存按单独计划接续，不因每日触发自动提交。

## 建议实施顺序

1. **封装WPS读取入口。** 优先消除当前远程剪贴板和文本编辑落盘步骤。现有browser_steps依赖CUA的直接DOM页面，不能直接对noVNC画布读取WPS DOM；容器实测也没有证明它已可无人值守调用。新增受支持的浏览器适配入口，执行前核对共享源码，运行后直接保存本次渲染日志，再交现有校验器。无需新增共享脚本或令牌。
2. **封装秀米只读候选搜索。** 先做搜索、分页和证据采集，明确区分未搜索完与确实未找到。输出候选及歧义供daily_check使用，不在搜索阶段创建副本或同步。
3. **补齐统一每日入口和浏览器占用保护。** 连接前两项、账本、完整性判断和通知；先跑“检查与提醒”完整链路，再加入修改动作。调度器只负责唤醒，入口负责真实执行状态。只加定时器不会补齐未实现的业务步骤。
4. **先做稿件检查器，再做修正器。** 将已验证规则转成明确检查项。修改前建独立副本与基线；已合规则跳过，结果未知先观察。保存后核对正文、内容图片来源/尺寸/加载及关键样式；复杂结构或不明封面标准转人工。避免全篇文本替换、按若干次Backspace或凭首图地址不同认定缺图。
5. **加统一整理结果通知，修复同步定位，最后做跨系统和连续运行验收。** 历史测试必须显式日期和测试标识，不把过去的例外扩展为日常规则。

## 执行分工与部署

确定的数据读取、完整性、顺序、已确认格式规则、保存差异检查、账本及通知适合程序处理。标题语义、同题复杂版本、未知备注及页面变化交agent判断；登录、验证码、平台协议及最终公众号核对由使用者处理。

当前Docker只有browser服务；AirScript在WPS平台执行，本机Python校验/账本/通知仍在宿主机，独立workflow容器尚未实现。后续可把Python执行与依赖统一放入workflow容器，浏览器作为独立服务；模型和Computer Use能力还需执行端适配，不会因为容器化而自动获得。迁移也需私有配置和状态，不能只交Git仓库。

无需为上述封装重新制作人工审核APP或公网接收服务。真实预约、稿件、登录数据及通知凭据继续仅保存在Git忽略目录。

2026-10-05后续：通知规则已按使用者要求细化；登录异常分别报告，同稿标题差异记录为非阻断提醒。已新增带--completion的格式/转存结果生成器，列出预约篇目、（头条）和标题差异，并核对同次运行与证据。其实际业务自动调用仍需统一入口接入，不能把生成器实现等同于排版/转存执行器已完成。
