# 浏览器通过后的首篇稿件验证

2026-10-02 范围更新：使用者确认日常只接收稿件，并依每日推送安排表的篇目与顺序整理基础格式。下一轮按 `docs/daily-push-validation.md` 验证一天的整组已接收稿件；单篇检查是其中的子步骤。无需另找来源账号，不要求对外转存。下面的副本、保存与证据要求仍适用。

使用一篇允许测试的稿件，优先选脱敏副本；由使用者提供该稿件入口并完成专用浏览器里的登录。不遍历其他稿件。

## 验证顺序

1. 记录稿件名称、入口和当前版本，保存编辑页与预览截图。
2. 核对可见标题、正文、图片、封面和落款；分别记录能读取、能截图核对和暂时无法取得的字段。
3. 先输出检查报告，不据猜测改写内容。现行标题、头尾图和封面规则需要用户确认；旧方案中的不同封面比例不能直接当作确定规范。
4. 如需测试修改与保存，使用稿件副本，明确本次修改范围，保留修改前后的证据；保存后重新打开核对实际结果。
5. 接管的 agent 重新观察页面、读取记录和证据，先核对上一步是否完成，再继续。

## 需要保留的结果

- 稿件定位、版本、检查范围与使用的规则版本。
- 能力矩阵：打开、读取文字、检查图片、预览、修改、保存、重开核对。
- 原始证据、问题清单、待人工事项与下一步。
- 每一步实际通过或失败的原因；不能把浏览器 localStorage 恢复测试等同于稿件任务恢复。

在首篇稿件闭环通过前，不启用定时业务任务。公众号操作、审核转发和最终发布另按明确授权处理。

后续进展（2026-10-03）：一篇明确候选已完成独立副本创建、标题测试标记保存、稿件库找回及刷新后内容核对。既有格式合规，自动修正错误格式仍待验证，详见[真实副本验证](real-copy-validation.md)。整组待确认事项继续保留。
