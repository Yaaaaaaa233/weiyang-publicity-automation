# 无人值守运营：授权、审批与失败可见性

2026-10-09 建立。依据 2026-10-09 的 Windows 真实运行日志（5 次审批全部 `allowed-once`、零拒绝）与主控核对结果。本文只讲**怎么让长期自动化少要权限、且失败不留盲区**，不含业务规则。

## 1. 审批为什么是瓶颈（机制事实）

- DSH **只有一次性授权**：没有 allow-always、没有记忆规则、没有授权存储，审批策略只有 `ask` / `never`。
- **生产读取即使只读也计中风险**。访问 WPS / 秀米账号页面本身就会触发审查。
- 高风险动作始终拒绝；**无人应答即 fail closed**。
- 结论：**批准次数随"被审查动作数"增长，不随会话新旧变化**。换新会话不会减少审批，也不会增加。

因此"少要权限"只有三条真实路径：

1. **减少被审查动作的数量**（把准备工作挪到业务轮次之外）；
2. **用一条明确指令预先授权**（Auto review 只比对"当前指令授权了什么"，不看你以前授权过什么）；
3. **消除可预见的基础设施动作**（见第 3 节）。

> **已核实（2026-10-10）**：此前只凭口述，现在有实测。10-10 那一轮的 Windows 报告写明「会话审批策略本轮为 `never`（不弹审批）」，并且**全程 0 次审批、0 次人工介入、无 `sandbox_permissions` 申请**；该报告在我能独立核对的每一项上都属实（155 项测试、`doctor` 双端哈希、逐项正文引用），所以这条采信。
>
> 结论：**在当前这台 Windows 执行机上，"每轮都要靠一条指令预先授权"已不再成立**——审批层被整体关掉了。第 2 节的四要素模板因此**降级为留档**：它仍然是写任务书的好格式（动作/目标/范围/次数写清楚对人对己都有用），但不再是"能不能跑通"的前提。
>
> **但这不改变本节的第 4 节（失败可见性）。** 审批消失只是少了一道闸门，不会让失败变得可见；反而更需要状态与回执，因为再没有"被审批拦下"这种显式信号了。另外要警惕一个反向风险：**审批是最后一道人工闸门，关掉之后 `never` 策略下没有任何交互式拦截**，所以"明确不授权"的清单必须在任务书里写死，靠代码侧守卫兜住（例如本项目的 `Stop` 失败关闭、去重不重放、不覆盖未知内容）。

### 明确达不到的目标

无人值守时段**必须有应答者**。中风险动作无法被设计成"自动通过"。任何声称"零审批跑完生产流程"的方案都与该机制冲突，不要据此规划。

## 2. 常态化授权指令模板

四要素缺一不可：**动作 + 准确目标 + 范围 + 次数/时长**。笼统的"允许我完成任务"不构成有效授权。

```
【常态化授权指令】
1. 工具 create_goal：注册本轮多轮生产流程目标。限 1 次。
2. 工具 schedule_create：创建上述一次性任务。限 1 次。
3. pwsh / Docker 读取类命令：核对容器、端口、卷与宿主机到容器的桥接；
   对 WPS 预约表与秀米稿件库只读访问（含浏览器驱动）。
   目标仅限本项目容器 <容器名> 与本项目浏览器 profile。
4. 秀米稿件库全库只读扫描、候选正文只读观察。
5. 独立副本创建 / 基础格式整理 / 保存与冷重开核对：仅限本次预约当日篇目。
6. 秀米「同步多图文到公众号」组合并提交到已配置公众号草稿箱：新提交上限 N 次。
7. 企业微信运营群结果通知：限 1 次，无论成败都要发一次结果。
8. （**2026-10-10 起默认不授权**）给本轮原稿与副本写入「转存好」标签：平台侧标签已暂停，改为只记私有账本。仅在需要刻意跑标签轮时才写入这一条授权，并同时设置 `WEIYANG_TRANSFER_TAGS=1`。
明确不授权：发布、操作公众号后台、重放任何历史同步、修改 WPS 共享脚本、
修改系统时钟、用缓存预约替代实时读取、清空或改写旧账本与去重记录。
```

把这段原样放进任务书。它在 2026-10-09 的实测里覆盖了当轮全部中高风险动作。

## 3. 可消除的审批来源

| 来源 | 为什么会产生审批 | 消除办法 |
| --- | --- | --- |
| 主机重启后容器不自启 | `compose.yaml` 无 `restart:`，需人工 `docker compose up -d` | 加 `restart: unless-stopped` |
| 会话预设回退 | 新会话默认 `workspace-write`，Docker/命名管道类命令逐条请求升权 | 运行会话固定 `preset=auto` |
| 运行中改部署 | 端口未发布、容器需重建 → 触发 `edit` + `pwsh` 两次审批 | 运行**前**把基础设施准备好，业务轮次不做部署动作 |
| 首次真实平台访问 | 首个生产页面访问即中风险 | 无法消除；纳入第 2 节指令预先授权 |
| **Docker 全天常驻占内存** | `restart:` 只管容器，引擎不开时容器也不会自启；使用者日常要把内存让出来 | 运行窗口：业务前 `runtime_window.py up`，业务后 `runtime_window.py down` |
| **退出 Docker Desktop 没有已被验证的安全 CLI 方式** | 强行结束进程可能留下 WSL2 残留 | 默认只做 `compose stop`（保容器与命名卷）；确需收回内存时，在私有 `local/runtime-window.json` 里配一条**已在本机验证过**的 `docker_desktop_stop_command` |

**原则：业务轮次里不出现部署动作。** 部署、重建、改配置都应在业务轮次之前完成并验证。

### 运行窗口：把引擎和容器的生命周期变成显式步骤

Docker Desktop 关着的时候，定时任务照样要能跑起来；跑完又要把内存还回去。这是"运行窗口"，由 `scripts/runtime_window.py` 承担：

| 命令 | 作用 | 不会做的事 |
| --- | --- | --- |
| `up` | 引擎不可达则启动 Docker Desktop → 等 ready → `docker compose up -d --wait` → 确认 running | 不重建镜像、不联网拉取 |
| `down` | `docker compose stop browser` | **不删命名卷**；不执行任何 `down`/`rm`/`prune`/`-v` |
| `status` | 报告引擎、容器状态与两个命名卷是否都在 | 只读 |

- **登录态放在命名卷里**：`weiyang-publicity_browser-data` 挂到 `/home/seluser/profile`，就是 Chromium 的 profile。**停容器、退 Docker Desktop 都不动命名卷**，所以不需要重新扫码；只有 `docker compose down -v` 会删它。`runtime_window.py` 的每条命令都过一道 guard，含 `down`/`rm`/`prune`/`-v`/`--volumes` 一律拒绝执行。
- **`SE_NODE_SESSION_TIMEOUT=86400`**：容器停再起，旧 Selenium 会话没了，第一次动作会重新 `start` 一个会话；profile 和登录还在。
- **业务轮次前自动兜底**：`Browser.reserved()` 现在先跑 `browser_runtime_preflight()`（容器起不来就报独立错误码 `browser_runtime_unavailable` 并写 `local/browser-image-drift/runtime-*.json`），再跑镜像比对。**只有"确证不可用"才阻断**：探针自己拿不到结论、或桥接层仍能摸到容器时，一律放行。
- 逃生阀：`WEIYANG_BROWSER_RUNTIME=0` 跳过运行窗口预检；`WEIYANG_BROWSER_KEEP_RUNNING=1` 让 `down` 不停容器（当天还要手动用的日子）。
- **`up` 在 Mac 上会 `open -a Docker`**，在 Windows 上会 `Start-Process` 启动 Docker Desktop；这是运行窗口的预期副作用，不是故障。

## 4. 失败必须可见

一次"触发成功但在读取阶段被截断"的运行，若不留回执，从外部与"任务从未创建"**完全无法区分**——2026-10-09 就发生过这种误判。

规则：

- 任一阶段发生致命错误而终止，**必须写出运行状态、失败代码与交接文件，并发出一条企业微信通知**，不得静默终止。
- 预览轮次同样适用：致命错误意味着本轮已经结束，"预览"不能成为静默的理由。
- 目前实现：`full_run` 的致命分支不再要求 `--execute` 才通知；`daily_run` 用 `notify_on_fatal` 控制，由外层入口 `full_run` 传 `False` 以避免重复通知。回归测试见 `tests/test_daily_wrappers.py::test_fatal_stop_in_preview_notifies_unless_an_outer_entry_owns_it`。
- 仍未消除的盲区：**历史业务日期读取无入口**（`wps_read.py` 对非当天硬拒绝），且该拒绝发生在任何业务动作之前。需要读历史日期时，只能由使用者单独授权或另建入口。

### 失败还必须可重试

"留下回执"只解决可见性；如果失败状态**无法重入**，一次瞬时故障就报废整个 run_id，运维只能换新标识——这会把一次抖动放大成一次人工介入。

2026-10-09 的 17:00 轮次同时暴露了三点，值得作为检查清单：

1. **跨时钟比较要留余量。** `generated_at` 来自平台云端脚本自己的时钟，与本机时钟差数秒；与脚本自身运行时长同量级时，零容差的"未来时间"判定会在 0 附近随机成败。同一模块链里已有一处对同一时钟允许 ±5 秒，新判定应沿用同一口径。
2. **失败态必须可重入。** 只读/判定/通知类入口没有下游副作用，失败后应当重跑而不是返回旧状态；返回一个没有 `observation` 的失败态，调用方裸取就会报出与真因无关的 `KeyError`，把诊断带偏。
3. **唯一文件名。** 证据文件普遍用独占创建（不覆盖）是好事，但**固定文件名会成为重试路障**：修好重入后第一个撞上的就是 `FileExistsError`。重试路径上的产物一律用唯一名字。

自检：故意制造一次读取失败，然后用**同一个 run_id** 重跑，确认它能走完而不是秒退。

### 部署漂移必须被识别，而不能只报"未知错误"

前两条讲的是失败要可见、可重入。还有一类失败更隐蔽：**代码是对的，但跑起来的不是这份代码。**

2026-10-09 17:40 的硬停就是这一类。`browser/Dockerfile` 用 `COPY scripts/browser.py /opt/project/browser.py` 把源码烘进镜像，`compose.yaml` 只挂数据卷；于是仓库改了 `browser.py` 之后，**运行中的容器仍然是旧的**。表现是 argparse 拒绝一个仓库里明明存在的子命令（`close-window`），而桥接层把它笼统报成 `host bridge error`——真因被完全掩盖，直到回传原始证据、逐字读出那段 usage 文本才定位。同一次漂移还缺 `hover-element` 与 `check-empty`，也就是说它同时卡住了转存标签，不只是正文采集。

规则：

1. **凡是从镜像取代码的路径，都要能回答"现在跑的是哪一份"。** 判据用**内容哈希**，不用时间戳、不用版本号。
2. **失败码要指向真因。** 子命令不被识别属于部署漂移，不是浏览器故障；给它独立错误码（`browser_image_stale`），并在消息里带修复指引。
3. **优先自愈，而不是要求人工重建。** 重建镜像要联网、且会重建容器（本项目已有"重建后锁残留、会话卡死"的前例）；`docker compose cp` 把仓库文件热替换进运行中的容器则不需要。容器在主机重启后存活，所以热替换能扛住真正的运行风险。
4. **自愈要留痕、也要留债。** 每次热替换写一条 `local/browser-image-drift/drift-*.json` 并置 `rebuild_pending`，把正式重建排到下一个自然维护点——否则热替换会悄悄变成永久状态。
5. **不要为了防一种故障而弄坏好路径。** 探针拿不到答案时（Docker 不可达等）必须**放行**，让真正的浏览器命令报出真实错误；只有"确证不一致"才阻断。已实测：Docker 未运行时 `doctor` 返回失败、预检返回 `None`，运行照常进入真实命令。

自检：把容器里的 `browser.py` 换成一个旧副本，确认下一次运行在**任何浏览器动作之前**以 `browser_image_stale` 停下、并留下 drift 记录；再把 `WEIYANG_BROWSER_SELFHEAL=0`，确认它改为失败关闭而不是自愈。

## 5. 运行前后检查清单

运行前：

- [ ] 容器 healthy，端口已发布，卷保留，登录态有效
- [ ] **容器内 `browser.py` 与仓库内容哈希一致**（`python3 scripts/browserctl.py doctor` 应报 `"match": true`；不一致时预检会自愈并记 drift，同时欠一次正式重建）
- [ ] **运行窗口可拉起**（`python3 scripts/runtime_window.py status` 报 `engine`、`container` 与两个命名卷；Docker 关着时 `up` 必须能把它拉起来）
- [ ] `compose.yaml` 已有 `restart:` 策略且已生效
- [ ] 私有配置齐备（含 `full-config`、`format-rules`、转存账本、通知配置）
- [ ] 全库测试通过
- [ ] **本轮触发的 `schedule_id` 已记录，下一轮的一次性任务已挂上**（见下方"定时任务会随会话消失"）
- [ ] 任务书内嵌第 2 节授权指令，且**时间与 run_id 只有一处定义**（`copy-*.cmd` 必须由请求文本单向生成，避免两份文件漂移）
- [ ] 唯一执行者；租约已释放

运行后：

- [ ] 取回回执包并独立核对哈希清单、通知回执、用量、提交次数
- [ ] 记录审批次数与事由、是否一次跑完、阻塞点
- [ ] **用量已归集进本轮摘要**（`scripts/collect_round_usage.py` 一步导出+导入；摘要仍为 `unknown` 就是漏了）
- [ ] **运行窗口已关闭**（`python3 scripts/runtime_window.py down`），命名卷保留
- [ ] 失败按"不重放未知提交、不改文字绕过去重"接续

### 定时任务会随会话消失

调度用的是 DSH 会话内的 `schedule_create`，**它活在会话里，不在 Windows 计划任务里**（全仓库没有 `schtasks` / `Register-ScheduledTask`）；工具契约本身就是"当前会话"——`schedule_create` 把提醒建在当前会话，`schedule_list` 只列"当前会话"的活跃提醒。会话重启、换会话、崩溃恢复都可能让未触发的任务消失；崩溃后重复投递也是已知行为。

**证据边界（2026-10-09 更正）**：我查到的那个空 `schedule_list` 是 **Mac 会话**的（主控在 Mac 上跑），**不代表 Windows**。能代表 Windows 的那次观察是 2026-10-08 的一次性任务"真实投递到原 Windows DSH 会话"（见 `docs/windows-temporary-automation-validation.md`）。**Windows 会话当前的调度状态尚未核对**，而三天试运行的补挂规则恰恰依赖它——所以这条规则按工具契约成立（机器无关），但必须在 Windows 上实测确认一次。且注意本仓库文档里的"本机"是**随文档而异**的：`docs/windows-deployment-preparation.md` 里的"本机"指 Windows。引用时写明是哪台机器。

规则：

1. **一次只挂下一轮**，不要一次挂三天：每轮跑完立刻创建下一轮，并把 `schedule_id` 写进本轮 `summary.json`。
2. 每轮预检时**检查下一轮任务是否还挂着**；没挂就立刻补挂，并**发一条企业微信告警**——"没有下一轮任务"和"业务失败"必须能分开看见。
3. 重复投递靠稳定的业务 `run_id` 去重，不靠调度层。

### 远程手动操作：每一步都必须可证伪

2026-10-10 凌晨在 UU 远程上连续做出过**两个错误结论**（先说"UU 不转发合成输入"，后编造"IOKit HID 层"机制），根源都是**测试设计不可证伪**。规则：

1. **"没有看见变化"不等于"动作失败"。** 点空输入框、按一个字母、点一片空白区域，本来就什么都不会发生。**每一个远程动作都必须选一个成功时有唯一、巨大视觉签名的目标**（开始菜单、右键菜单、文件管理器窗口、控制台窗口）。做不到就别做这个测试。
2. **不许目测坐标。** 用脚本从截图里量真实像素（本例：两个桌面图标在窗口内分别是 x 87 与 x 159、y 64，文字标签在 y 83–94；肉眼估的 (118, 85) 正好落在两图标之间的空白处，白白浪费了一轮排查）。驱动的 `click(debug_image_out=…)` 会画出红色十字准星，是确认坐标空间的正确手段。
3. **分清单位。** `click` 的 `x,y` 是**窗口局部截图像素**；回报的落点是**屏幕点**；主显示是点位不是像素（本例 1470×956 pt @2x，而窗口截图 1568×961 px）。把两者混起来，会得出"点在屏幕外"这种完全错误、还会自我印证的结论。
4. **窗口尺寸/位置会变**（本例中途从 1567×1033 变成 1568×961）。**每次动作前重新截图取坐标**，不要复用上一轮的。
5. **不许为结论编机制。** 查不到原因就写"原因未知"。编一个听起来合理的机制（如"在 IOKit HID 层读输入"）比留空危害大得多，它会污染后续所有判断。
6. **先查本项目已有的坑。** 指针落点偏移这个问题**2026-10-05 就记录过**（`local/windows-check-20261005`：「UU 鼠标落点偏移，已恢复兼容模式」）。遇到远程输入类故障，先在 AGENTS.md 与 `local/*/state.json` 里搜一遍同类记录。
