# 封装完善与 Windows 三天试运行方案

> 2026-10-12 更新：后续修复、验收顺序及三天试运行启动条件以 [下一阶段修复与完整验收方案](next-stage-repair-plan.md) 为准。下文旧日期与测试数字保留作为历史安排，不表示三天测试已开始。

当前安排：完整业务验收向 Windows 当前执行会话直接投递拟用于定时任务的固定提示词，无需另建临时定时任务；“转存好”平台标签保持关闭，防重与迁移以私有账本为准。验收通过后再在新标准模式、Auto review 会话开展三天真实定时运行，核验调度并采集常态成本；当前长对话用量单独归为调试/验收。

日期：2026-10-08。状态：第一阶段封装与第二阶段部署预检完成；临时无人值守首轮异常分支已验收，完整成功路径及三天试运行尚未完成。

## 本次安排（2026-10-09 定）

| 项 | 值 |
| --- | --- |
| 目标 1：一次定时全流程 | **2026-10-10 09:30（Asia/Shanghai）**，run_id `win-temp-20261010-0930-1010` |
| 目标 2：三天试运行 | **2026-10-11 → 2026-10-13，每日 17:00**，标准模式新会话，一 session 一任务 |
| 每轮触发 | DSH 会话内 `schedule_create` 一次性任务，**每轮跑完立刻挂下一轮** |

选 09:30 而不是 17:00，是为了证明**触发时间可以任意设**，不是只有在常态时刻才生效；`wps_read` 只接受当天业务日期，所以这一轮读的是 10-10 当天的真实预约。三天试运行回到 17:00，数据才有代表性。

前置（硬性）：r4 补丁必须先在 Windows 落地并跑出全库通过、`browserctl doctor` 报 `match: true`；容器里缺 `close-window`/`hover-element`/`check-empty` 时，全流程必然死在正文采集收尾或转存标签。

`schedule_create` **活在会话里**（工具契约是"当前会话"）：会话重启、换会话或崩溃恢复都可能让它消失，也可能重复投递。所以一次只挂下一轮，把 `schedule_id` 记进本轮摘要，并在每轮预检时确认下一轮还挂着；没挂就补挂并发告警。重复投递靠稳定业务 `run_id` 去重。见 `docs/unattended-operations.md` 的"定时任务会随会话消失"。

**前置核对（未完成）**：这条规则建立在工具契约上，机器无关；但**三天试运行挂在 Windows 会话上，而 Windows 会话的调度状态尚未核对**。开跑前先在 Windows DSH 里 `schedule_list`，并确认 2026-10-08 那个一次性任务是否还在——这决定补挂规则是"必须"还是"保险"。

## 目标与现状

完善可迁移的执行流程和日志，在 Windows 上完成一次临时自动化验收，再用 DSH 新会话连续运行三天，为 demo、成本评估和长期日志管理提供数据。

目前 Windows 有监督流程已完成预约读取、稿件匹配、副本保存重开、一次同步提交和企业微信通知；新版 Mac/Windows 136 项测试通过。上一轮公众号草稿箱结果已由使用者确认正常，原 Windows 账本已记确认，提交次数仍为 1。组合选稿曾需临时恢复，DSH 单轮用量导出已完成真实样本验证，日常运行须在模型开始前建立测量窗口；无人值守与业务成本样本仍待验收。

## 每轮业务流程

预检并领取任务 → 实读当天 WPS 预约、头条及备注 → 核验秀米登录与近 14 个自然日候选 → 根据正文、部门、日期、周次和版本确认稿件 → 收齐后整理独立副本 → 保存重开核对正文、图片、头尾图、分隔符、间距及封面 → 标注了头条则头条置首，否则按预约表行序，其余按预约行序组合 → 提交一次公众号草稿箱同步 → 发送企业微信结果 → 保存摘要、释放租约。

无预约也通知。登录异常单独报告，不当成无预约或缺稿。标题不同但有证据确认同稿时仅提醒、不阻断；缺稿、错周次或未解决版本歧义阻断整组整理。正文身份核验可以使用 agent，但必须通过固定接口留下结构化证据，不能只凭标题相似度。

转存无明确成功证据时，以“转存待确认”结束并提醒，由使用者核对公众号后台；不重复提交，不操作后台，不发布。上一轮待确认任务先由使用者核对，并沿用原账本确认。

## 日志与容量管理

以下为拟实现的格式和初始保留策略，三天试运行后按实际体积调整。

| 文件或记录 | 核心内容 | 保留策略 |
| --- | --- | --- |
| 每轮 `summary.json` | run_id、业务日期、实际时间、电脑、版本、各阶段状态、篇数、耗时、重试、人工介入、Token、日志体积、证据索引 | 长期保留精简摘要 |
| 每轮 `events.jsonl` | 步骤开始结束、错误类别、恢复与验收结果；追加写入，接续沿用 run_id | 90 天，结束后可压缩 |
| 每轮 `usage.jsonl` | 调用时间、模型、请求 ID、普通输入/缓存输入/输出 Token、用量来源、费用依据 | 90 天；汇总长期保留 |
| 私有证据 | 正文基线、图片清单、关键截图、页面快照与回执 | 正常 14 天，异常 90 天；未解决任务暂不清理 |
| 去重与任务账本 | 源稿/副本映射、同步提交次数、通知去重及任务所有权 | 独立保留，不随普通日志清理 |

证据按内容哈希去重，默认仅保存关键验收点；出错时保存前后状态。日志按日期和运行标识分目录，轮转、压缩并清理到期文件。实施时配置总容量上限；空间不足时提醒并停止新增大证据，不能删掉未完成任务所需证据。所有凭据、Cookie 和登录数据排除，稿件与运行日志仅放私有目录，不提交公开仓库。

用量必须按运行时间边界和真实调用记录归集。恢复属于同一 run_id，新每日执行使用新 run_id；相同请求记录去重。费用根据真实模型及当期价格计算，不能直接把缓存输入与普通输入相加计费。DSH 无法提供某字段时记为未知；会话界面累计值不算单轮用量。部署、调试和日常执行分别统计。

每轮收尾用一条命令归集（`docs/run-logging.md` 的"一步归集"）：

```sh
python3 scripts/collect_round_usage.py --run RUN_ID --date YYYY-MM-DD \
  --session <私有session.v4.jsonl[.zstd]> --start 带时区时间 --end 带时区时间 --turn N
```

窗口端点要对齐到真实事件的整数毫秒（`step/start.time`），否则导出以 `Call crosses execution boundary` 拒绝。摘要仍显示 `usage: unknown / requests 0` 就是这一步漏了——**那不是零消耗**。

## 无人值守边界与交付

Auto review 不保证所有动作获批；保持审查机制，通过固定、范围明确的操作和预检减少审批阻断。扫码、验证码、协议或新增授权仍由使用者处理。因审批中断的临时验收不记为通过；常态运行发生此类问题时记录并提醒。

交付：更新并推送的仓库、Windows 部署与新会话交接说明、固定任务提示词、一次直接投递的完整业务验收报告及账本防重/迁移验证、三天日志和用量汇总，以及 demo 素材、成本评估和长期保留建议。三天中无预约、缺稿等业务结果不等于执行失败；但若未出现可整理转存的预约，不宣称三天覆盖了全部成功流程。
