# 转存标签与候选正文复核

2026-10-08 补丁：149 项 Python 测试通过。用 Windows 真实目录快照离线回放 219 篇全库中的 29 篇近期稿，先前误报缺稿的一条标题差异较大的预约现在被召回为排名第一的待正文核验候选；这没有自动确认身份。同期其他两条无冲突标题保持唯一精确匹配。标签编辑器经 Windows 只读观察，尚未在真实稿件上添加标签。

## 查稿

近 14 个自然日范围保留。明确周次、预告/回顾冲突仍从自动候选中排除。部门标题元数据冲突保留在排序候选中，标为未确认并要求正文复核，避免把实际存在的稿件报成缺稿；标题相似度不能覆盖该冲突并自动确认。完整标题唯一且没有部门冲突时沿用自动匹配；找不到完整标题时，不再用 0.45 阈值判定缺稿。其余候选按字符相似度降序保留，最高候选先采集正文；没有 top-K 截断。主题、部门、日期、周次及版本仍按实际正文证据核验。多候选逐份记录不同稿/同稿与版本选择理由。

每行观察新增 search_audit、review_rank、similarity、exclusion_reasons、processed_candidates。原始目录与正文观察在私有目录保存；身份决策引用各自正文证据。多候选未核验时通知“存在多个相似候选，需结合正文核对（不代表同稿多版本）”；空候选通知为“未匹配到对应稿件（不代表未转存，需复核）”。已处理的完整同题稿报告“已转存或已有提交预留”，停止重复整理，不改报缺稿。

当前正文接口会采集全部候选并按排名返回 agent；不是只读第一篇后就宣称同稿。候选较多时的调用与证据体积需要实测，不能沿用旧样本估算。

## 转存与标签

**2026-10-10 使用者决定：平台侧标签暂停。** 原来的顺序是「明确平台成功 → 企业微信 accepted → 给原稿和转存副本添加“转存好”」，现在**不再往平台稿件上写这个标签**。理由：它唯一的读者就是这个自动化自己（`xiumi_scan.py:166` 用它把已转存稿从候选里剔除），而**私有转存账本已经在做同一件事、而且更早**——`transfer_registry.reserve()` 在转存**之前**就按 id 登记 `reserved`，`xiumi_scan` 再用 `annotate()` 按卡片 id 挂上状态。也就是说它是**冗余记账**，却要写在**收到的原稿**上，而那不是我们的作品。结论：**内部状态记在内部。**

- 开关：**默认关闭**，只有 `WEIYANG_TRANSFER_TAGS=1` 才跑标签轮。关闭时 run 在通知 accepted 之后直接进入 `completed`，并把账本记为 `tag_status: paused_by_operator`——**不谎报 `verified`**。
- **代价（明确记录，不是遗漏）**：账本成为**单一真相源**。账本丢失或迁移漏带时，平台上再也看不出哪篇处理过，可能出现重复转存。`docs/full-runner.md` 本来就要求私有账本随迁移保存，现在这条从"锦上添花"变成**承重**要求。
- 适配器代码与离线测试**保留**（`transfer_tag_ui` 仍在私有配置里）；将来若要启用，设那个环境变量并跑一轮**标签专用接续**即可，不必重跑整条链路。
- 另外：**给副本打标签本来就是多余的**——副本标题带托管前缀，早已被 `xiumi_scan` 的 `managed_copy` 规则排除。

只点击提交、进度消失、超时或未知回执仍不构成成功。

sync_workflow 新增 observe-result，只观察原组合窗口的显式可见成功对话框，并重新校验同一目标、顺序及封面；保留平台快照、成功记录与原提交预留。未知点击不自动重试；缺少明确成功证据仍 awaiting_confirmation，此兼容状态名不意味着强制人工审批。旧的实际用户确认入口保留用于历史任务，不作为新运行的必经步骤。平台成功对话框的实际布局与消息措辞仍待 Windows 实机验收，不扩大到任意页面文本匹配。

full_run 保存转存、通知、标签三个检查点。通知不成功为 notification_pending；标签未通过为 tagging_required。标签暂停期间（默认）终态是：确认 + 通知 accepted → `completed`，账本 `tag_status: paused_by_operator`。同 run_id 接续时只观察结果、复用去重通知，或（仅在显式开启时）补标签，不重读并编辑已提交稿件、不重发同步。即使跨执行日，也只接续原业务日期的提交结果和标签。

账号级 data/transfers/account-*.json 在组合提交前记录源稿/副本映射与预留；同源稿的新运行拒绝再次提交。标签完成需刷新稿件库核对每个 ID 后才记 tagged。标签被删仍由账本防重；转存成功但通知/标签失败的稿件也仍受保护。迁移必须带这些私有记录及原同步账本，并维持唯一业务执行者；两台机器各自独立空账本不具备跨机器防重。

## 标签界面适配与接续

transfer_tags 是受限 UI 适配器，只操作当前稿件 ID 的标签按钮、指定标签面板、固定文字“转存好”，保留已有其他标签。未知布局停止，不猜坐标或重放同步。复用同一稿件库窗口；每次搜索核对全部标签范围、完整标题、实际 ID 和账号，保存后刷新并重新搜索核验。

2026-10-08 Windows 只读实机观察确认：标签按钮位于 `div.show-item` 的 hover 遮罩内，必须先用 WebDriver Actions 将真实鼠标移到当前稿件卡片，再重新观察按钮可见后点击。对话框类为 `tn-dialog-item-tag-edit`；已分配标签列表是 `ul.tag-list.item-tags`，可选全局标签列表是 `ul.tag-list.all-tags`，标签选项为 `li.tag-item`（该 `li` 的 own_text 为空，需按 rendered_text 精确比对），新建输入框 placeholder 为“添加新标签，回车确认”，确定按钮为“确定”。只读检查取消了对话框，未改稿件标签。

私有配置 `transfer_tag_ui` 使用字段：`panel_class`、`choice_class`、`current_list_class`、`choice_list_class`、`new_placeholder`、`save_text`、`evidence_paths`。新标签通过该输入框回车；只有观察到它已分配到当前稿件，或作为全局选项出现后又确认分配到当前稿件，才会保存。点击“确定”后关闭面板，并按稿件 ID 刷新、重新搜索验证标签。已分配标签检查与已有标签选择不得依赖 CSS 选中样式，因为实测页面没有 selection marker。Windows 真正添加、刷新重开和已提交任务接续仍待实机验证。

标签 UI 配置可以在原提交后补充；业务配置、账号、目标和原稿映射不能改变。使用原配置与原 run_id 接续 full_run --execute；tag_request 指明待处理稿件，tag_error 保存实际失败，agent 可观察并配置后继续。

本轮单测覆盖低分候选召回、排名、部门冲突送正文复核、周次硬冲突、已处理识别、hover 显示后精确点击、精确标签读取与接续、跨运行防重、未知提交不重发、平台成功与通知成功的标签门槛。Windows 只读发现现存同步证据中没有捕获秀米明确成功提示，因此提交成功判定仍未实机验证；没有新的成功任务时不为试验而重复提交。
